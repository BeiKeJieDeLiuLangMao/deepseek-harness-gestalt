# Agent Note: Build the Desktop account pool around an embedded CLIProxyAPI core

Status: implemented

English | [中文](2026-09-09-built-in-cliproxyapi-account-pool.zh.md)

## Problem

DeepSeek Gestalt previously offered a Desktop-only Sub2API component that the user downloaded and enabled after installation. The Desktop Host installs an out-of-tree Harness plugin and a runtime pack, restarts the Web Host, and renders the sidecar's management workspace inside Settings. That design pays for an independent plugin release, PostgreSQL and Redis, an installation state machine, and an embedded foreign UI before the user can add an account.

The replacement makes the account pool part of the Desktop Bundle. It supervises one local CLIProxyAPI core, presents a Gestalt-owned account and quota experience, and publishes one usable model provider without exposing management credentials to the renderer. The product keeps a durable source relationship with the upstream core and carries GLM Coding Plan through a separately reviewed clean-room implementation in the Gestalt fork.

## Decision

The remote coordination record is [gestaltrun/deepseek-harness-gestalt#649](https://github.com/gestaltrun/deepseek-harness-gestalt/issues/649). It tracks this proposal and its delivery graph. [Issue #652 comment 5609234949](https://github.com/gestaltrun/deepseek-harness-gestalt/issues/652#issuecomment-5609234949) freezes the GUI planning input described below without marking runtime or provider implementation evidence complete.

DeepSeek Gestalt ships CLIProxyAPI as a built-in Desktop component. The initial upstream baseline is lightweight tag `v7.2.155`, which resolves to commit `7fac6b15bcfe5ea55c18c9eaec8e5b7e6457d974`. The Desktop Bundle contains a platform binary built from an exact commit of [`gestaltrun/CLIProxyAPI`](https://github.com/gestaltrun/CLIProxyAPI), a GitHub fork whose parent and source remain [`router-for-me/CLIProxyAPI`](https://github.com/router-for-me/CLIProxyAPI). The harness repository records that core as a Git submodule pin. Application startup does not download, install, or enable the core, and Settings does not retain an Offer card.

The manager UI source is imported from `router-for-me/Cli-Proxy-API-Management-Center` commit `ed5f1c48e11ba7335f1e8f676f228c280196af85`, licensed under MIT with the verified `Copyright (c) 2026 Router-For.ME` notice, into a first-party client package in this repository and then evolve as Gestalt source. The import preserves the applicable copyright and permission notice. It uses the existing Desktop Settings shell, slots, components, locale, and theme. It is not a UI submodule, a runtime download, an iframe, or a remote management page.

The frozen draft uses prototype source `beaeec5475e4e0d85e957018da677f34e85a94a1` and external evidence commit [`01e7c2e4c3c2e6e46aabd46a54dc85fc90c49a75`](https://github.com/gestaltrun/deepseek-harness-gestalt/tree/01e7c2e4c3c2e6e46aabd46a54dc85fc90c49a75/issue/649/beaeec5). Its durable inputs are the [experience route](https://github.com/gestaltrun/deepseek-harness-gestalt/blob/01e7c2e4c3c2e6e46aabd46a54dc85fc90c49a75/issue/649/beaeec5/experience-route.md), [Variant A management view](https://github.com/gestaltrun/deepseek-harness-gestalt/blob/01e7c2e4c3c2e6e46aabd46a54dc85fc90c49a75/issue/649/beaeec5/01-a-management.png), [quota and unknown-state view](https://github.com/gestaltrun/deepseek-harness-gestalt/blob/01e7c2e4c3c2e6e46aabd46a54dc85fc90c49a75/issue/649/beaeec5/02-quota-and-unknown.png), [Kimi device-flow view](https://github.com/gestaltrun/deepseek-harness-gestalt/blob/01e7c2e4c3c2e6e46aabd46a54dc85fc90c49a75/issue/649/beaeec5/03-kimi-device.png), and [empty GLM key form](https://github.com/gestaltrun/deepseek-harness-gestalt/blob/01e7c2e4c3c2e6e46aabd46a54dc85fc90c49a75/issue/649/beaeec5/04-glm-empty-form.png). Production adopts Variant A's information hierarchy and the quota/time marker on one axis. It removes the prototype switcher and fixture-only Composite, fixed `8317`, and healthy-state claims; labels enable and disable actions accurately; masks GLM secrets; improves responsive card fit and contrast; and uses a needle consistent with its legend. The packaged Electron WDIO fixture route proves the composition and interactions at the named prototype revision, not a real CLIProxyAPI process, account, OAuth flow, credential, quota response, model registration, or inference request.

The replacement starts with an empty CLIProxyAPI home. It does not read, convert, import, or remain compatible with Sub2API accounts, credentials, statistics, quota history, Composite groups, routes, or data formats. Removing old user data is a separate destructive operation and is not implied by this decision.

## Package and source topology

The CLIProxyAPI source pin is a catalog child outside `pnpm-workspace.yaml` and TypeScript project references. CI jobs that build or inspect the core initialize submodules recursively and verify that the gitlink resolves to an existing commit in `gestaltrun/CLIProxyAPI`. Jobs that do not need the core source may retain an uninitialized child. The existing Desktop `extraResources` assembly and packaged/development path split carries the core without consulting the user's default config or `PATH`: packaged runs resolve a locked Resources manifest and binary, while development resolves an explicit build output.

Gestalt-owned TypeScript code remains in the harness repository. It contains the Desktop process supervisor, the narrow management gateway, the LLM adapter integration, the renderer projection, and the native Settings UI. The Go fork contains upstream CLIProxyAPI plus the accepted GLM subscription implementation. That core change is owned by the separate `codex/feature-glm-coding-plan` delivery in the fork; this harness decision consumes its verified capability and final commit pin rather than duplicating Go implementation ownership. No Host or renderer package imports Go source through workspace paths.

A fork update uses a reviewable branch and pull request in `gestaltrun/CLIProxyAPI`. The update identifies the upstream base, retain or deliberately revise the Gestalt GLM delta, and pass the fork's checks before the harness gitlink moves. Moving the harness pin is a separate reviewed change with Desktop packaging and runtime evidence. Neither repository floats on upstream `main` or the latest release tag.

The catalog of independently released Harness plugins remains useful, but its Sub2API-specific topology is superseded for this account pool. The shipped product retires `sub2api-sources`, its writer and catalog, installer, profile surgery, and Offer lifecycle; it does not retain a network fallback that downloads the core when packaged resources are absent. The historical [Sub2API Offer-card decision](../../archived/architecture/2026-08-28-sub2api-offer-card-installer.md) is archived; do not restore an Offer iframe, one-click sidecar installer, or physical deletion of `$DSH_HOME/sub2api` user data.

## Runtime ownership and lifecycle

The Desktop Host owns one CLIProxyAPI process per isolated Desktop instance. A supervisor with a small lifecycle interface hides binary selection, configuration generation, loopback addressing, process spawning, readiness, crash recovery, shutdown, and diagnostic identity. The renderer and the Web Host do not spawn or discover the process independently.

The process binds only to loopback on a per-instance dynamic port. The inspected upstream configuration defaults to port `8317`, and port-zero behavior is not established because the core does not report an assigned port back through its config. Releasing a Host-reserved port before spawn does not prove exclusive ownership and is not accepted as a race-free design.

The runtime ticket must prove the chosen mechanism with a focused ownership test before publishing the endpoint or either key: a competing listener must be unable to receive management or inference credentials, the supervisor must identify the spawned process as the listener, and startup must fail without credential disclosure when ownership cannot be established. The implementation may add an explicit inherited-listener or assigned-port handshake to the fork, or another mechanism that satisfies this evidence; it may not claim safety from reserve-then-release alone.

Desktop startup admits the account pool only after the core reports readiness from the expected binary and configuration identity. A startup failure leaves the rest of Desktop available with an actionable account-pool failure state. Unexpected exit enters bounded crash recovery under the same supervisor; repeated failure stops respawning and preserve diagnostics without claiming that the provider is usable. Desktop shutdown cancels recovery, terminate only the process tree owned by that instance, and wait for the port and process identities to disappear.

The Desktop Bundle carries the binary for each supported packaging target. The initial required matrix is macOS arm64, macOS x64, and Windows x64, matching the existing native release runners. Each target runner builds the core from the initialized submodule on that target rather than assuming a cross-compile path. CGO and dynamic-library requirements are an implementation preflight: a target that is not self-contained must fail packaging with its missing runtime dependencies identified. Any additional target requires an explicit product decision and a matching build lane.

A generated core manifest binds `sourceSHA`, operating system, architecture, binary resource path, and SHA-256. Packaging and startup reject a missing manifest or binary, an architecture mismatch, a digest mismatch, or a source identity that does not match the submodule pin. First launch requires no Go toolchain, PostgreSQL, Redis, core download, user `PATH`, or default CLIProxyAPI configuration.

## Management authority and renderer projection

The Desktop Host creates and retain separate CLIProxyAPI authorities for management and inference. The management secret is available only to the Host management gateway. The inference API key is available only to the local LLM integration that needs to call the OpenAI-compatible inference endpoint. Neither value enters renderer props, browser storage, session logs, screenshots, diagnostics, or retained artifacts.

The management gateway exposes only product operations: read the redacted account roster, begin a supported login, observe its status, cancel its OAuth session, apply supported auth-file mutations, and request quota refresh where a verified provider probe exists. It does not expose CLIProxyAPI's generic management request facility to the renderer. Active quota probes use Host-owned, fixed provider endpoint policies adapted from the imported manager logic; the renderer chooses an account and request refresh, not supply an arbitrary URL, method, headers, or management payload.

Anthropic, Codex, and Antigravity start PKCE redirect flows by default. Kimi and xAI use device authorization: their auth start returns `flow=device`, `user_code`, `expires_in`, `url`, and `state`. Login URLs, user codes, expiry, and state are returned only in the minimum form required for the Desktop Host and UI to complete the verified flow. The UI shows waiting, success, failure, expiry, cancellation, and retry without treating a device flow as an embedded redirect.

One Host-owned immutable snapshot projects component health, redacted account identities, login operations, quota observations, freshness, and actionable failures. External changes are published only after their operation commits. Components consume the snapshot through the client slot injection machinery and send intents through narrow callbacks; they do not poll CLIProxyAPI, mirror secrets, or become a second account authority.

The account cards support the accepted interaction rule: a page-level control switches all cards between management and quota faces, while each card retains an individual flip action. A global switch resets card-specific exceptions and establish one predictable face for the whole grid; subsequent individual flips create visible local exceptions until the next global switch. Placement, density, and motion may vary placement, density, and motion but may not remove either operation.

## Provider registration

The integration publishes one stable DSH provider route for CLIProxyAPI rather than one route per account source or a replacement Composite concept. Kimi, Codex, Anthropic, Antigravity, xAI, and the proposed GLM subscription are account-pool sources behind that route. CLIProxyAPI remains responsible for choosing an eligible account for a model request.

The adapter derives its model catalog from the local core's `/v1/models` response, including display names, context windows, output caps, and think-level ranges. The ordinary OpenAI listing strips those fields, so the catalog request identifies as Grok Shell in addition to the harness User-Agent. When Desktop settings and credentials are present, it writes that catalog onto the Models-page `llm-pi-ai` provider `gestalt-account-pool`. The Host already injects the inference key as `DSH_GESTALT_ACCOUNT_POOL_API_KEY` in the process environment; the plugin does not rewrite a read-only env value into the credentials file, and a failed credential write does not skip the catalog. It does not also register a second `ctx.llm` adapter for the same route. Without those seams it registers, replaces, or withdraws the single route atomically through `ctx.llm`. An empty account pool, an unavailable core, or a catalog that cannot substantiate a usable model does not publish a falsely usable route. The product-owned route id is `gestalt-account-pool`; it is distinct from the conventional user-configured `cliproxyapi` id and fails loud rather than replace any existing route with the same product id. Auth files live in a stable `auth/` directory beside generation-private TLS and config, so a later generation keeps the same accounts.

Management and inference remain separate authorities even though they address the same local process. UI account mutations must not be required for ordinary inference after the adapter has captured a valid endpoint and key, and an inference consumer must not gain management operations by possessing its request configuration.

## Quota observations

CLIProxyAPI does not provide one uniform active quota endpoint. The imported manager source contains provider-specific active quota implementations whose React-free data modules and shared quota utilities are adapted into Host-owned policies: `src/features/quota/providers/*/data.ts`, `src/utils/quota/{constants,parsers,builders,resetInstants}`, and `src/types/quota.ts`. The minimum portable closure also includes the quota-facing `AuthFileItem` type, `normalizeAuthIndex`, and the `DAY_MS`, `HOUR_MS`, and `MINUTE_MS` constants; its i18next dependency is type-only and is a local translation-function signature rather than that UI framework. `QuotaTimeline`, `quotaTimelineModel`, `QuotaMeter`, and `AuthFileQuotaSection` are direct UI foundations to adapt into the first-party account cards, not proof that the original manager's browser-direct management architecture should remain.

The initial active matrix covers all five login providers. Anthropic reads OAuth usage windows including `five_hour` and `seven_day` utilization and `resets_at`. Codex reads wham usage with `used_percent`, `limit_window_seconds`, and reset values. Antigravity reads `retrieveUserQuotaSummary` buckets with `remainingFraction`, window, and `resetTime`; `5h`, `five-hour`, and `five_hour` normalize to five hours, while `weekly` and `week` normalize to 168 hours. Every other window keeps `periodHours=null`, preserving balance and reset facts without drawing a time tick. Kimi reads `/coding/v1/usages` usage and `limits.window` duration/time unit. xAI reads period usage from `cli-chat-proxy.grok.com/v1/billing`; the manager's paid `POST` chat ping with `max_tokens: 1` is not imported. When billing or `/me` cannot establish quota, the result remains unknown rather than sending an inference request. The Host normalizes only verified response fields and retain their provider, provenance, collection time, and last successful observation.

A quota value distinguishes known, partial, probing, stale, unknown, unsupported, and failed states. Unknown or unsupported data never render as zero, full, or a fabricated balance. A quota line may show remaining capacity only when a source supplies the required numerator and denominator. The overlaid time-window percentage is calculated only when the source supplies enough information to establish the window duration and reset position; a reset timestamp without a duration does not produce a time percentage.

For GLM Coding Plan, inference and `/models` use `Authorization: Bearer <key>`, while the quota request uses the raw key in `Authorization`. Personal quota is read from `{open.bigmodel.cn|api.z.ai}/api/monitor/usage/quota/limit`. Team quota adds `?type=2` and the `bigmodel-organization` header, plus `bigmodel-project` when the account names a project. A 401 or 403 reports failed credentials without overwriting the last valid quota snapshot.

GLM quota prefers `TOKENS_LIMIT` entries and uses `CREDIT_LIMIT` only when no token limit exists. Unit `3` identifies the five-hour window and unit `6` the weekly window. The projection retains `used_percent`, `reset_at`, and `updated_at`; it derives remaining capacity from verified used percentage and draws the time comparison only when the window duration and reset position are established. The subscription base's `/models` response is authoritative for GLM model availability, so the integration does not invent a static GLM catalog.

The manager implementations establish the complete provider matrix and parsing basis, while live-service validation remains acceptance evidence rather than a missing design input. Product behavior therefore labels unverified, failed, or expired observations as unknown or stale, preserve the last valid snapshot on authentication or transport failure, and avoid claiming that every account currently returns every documented field. Refresh cadence and cache lifetime are bounded Host policy chosen to avoid repeated upstream calls, with provider-focused tests rather than a renderer polling interval. Quota observations are display and diagnostic facts only. Codex reset-credit count may be read and displayed, but reset-credit consumption and reset operations are outside this delivery, and Gestalt does not invent a remaining-percentage threshold that disables an account or changes routing. CLIProxyAPI's standard eligibility, cooldown, and scheduler behavior remains authoritative. The UI may use labeled fixtures for every state but does not imply that a fixture field has passed live-service validation.

## GLM subscription status

The candidate GLM Coding Plan behavior comes from the official `Wei-Shaw/sub2api` source at commit `98d86915becae9fe9491a91ffc6defd5235c8d2b`. It uses a subscription data-plane API key supplied by the user and selects the Coding Plan endpoint and quota semantics with `account_mode=coding`. It has no OAuth token provider, browser login, or refresh-token flow.

The Gestalt UI therefore offers a dedicated GLM Coding Plan key entry rather than adding GLM to the five OAuth login actions. That entry explicitly selects region (China or international) and account scope (personal or team); it does not infer either from the key or silently fall back to pay-as-you-go. Team accounts additionally require an organization id and may name a project id. The Host stores these values through the credential-owning path and passes only the resulting authority to the core. GLM remains an account source behind the single CLIProxyAPI provider. The core's Chat translator satisfies the DSH protocol, so Gestalt does not require a separate Anthropic-specific GLM endpoint. Its OpenAI-compatible effort normalization maps ordinary `low`, `medium`, and `high` requests to GLM `high`, and `xhigh` or `max` to GLM `max`; the exact `glm-5.3` model preserves explicit `low`. Anthropic-compatible GLM 5.3 requests preserve the corresponding `low`, `high`, and `max` levels rather than passing unsupported spellings through.

China personal and international personal Coding Plan keys are the selectable live paths. Team inputs use the same credential model when the user supplies an organization id and optional project id, but this delivery proves their request construction with fixtures and does not claim live success for all region-and-scope combinations. The product does not add subscription purchase, organization discovery, project discovery, invitation, or billing administration. The verified China Coding base is `https://open.bigmodel.cn/api/coding/paas/v4`; the ordinary `https://open.bigmodel.cn/api/paas/v4` pay-as-you-go base is a different product and must not be substituted. The verified international Coding base is `https://api.z.ai/api/coding/paas/v4`. International quota uses the `api.z.ai` origin. Missing region configuration makes the account unavailable instead of redirecting it to China or pay-as-you-go.

The source is identified as LGPL-3.0 while the target core is MIT. The shipped implementation treats the official Sub2API behavior as protocol evidence and independently implement Coding Plan on CLIProxyAPI's existing MIT executor, translator, auth, and model extension points. It does not copy Sub2API source code, comments, tests, or expressive structure. GLM remains required product scope under this approach.

A static port of the Go implementation remains a permitted alternative rather than a dismissal of the feature. It would require the distribution to satisfy the applicable combined-work relinking and accompanying-material obligations and would add a mixed-license maintenance burden to the core fork. The complete field inventory and license report must verify the exact license notice and obligations before either path freezes; this proposal does not infer whether the source grant is LGPL-3.0-only or LGPL-3.0-or-later. Repository README and LICENSE text must state only the verified grant and the obligations of the chosen implementation.

## Alternatives considered

**Retain the downloadable Offer card and out-of-tree sidecar plugin.** Rejected because the user chose a built-in Desktop capability. The single Go core no longer justifies a separate enablement download, Web-profile surgery, or a plugin release train carrying PostgreSQL and Redis.

**Embed the official manager UI in an iframe or keep it as a UI submodule.** Rejected because the account-pool experience must use Gestalt components and evolve independently from core updates. An embedded manager would also put a broad management client in the renderer instead of preserving the Host authority.

**Vendor the CLIProxyAPI source directly into the harness repository.** Rejected because a submodule records an exact foreign-source commit while preserving the fork's review and upstream relationship. Copying the Go tree would obscure upstream synchronization and mix its build graph into the TypeScript workspace.

**Keep the core integration in another Gestalt sidecar repository.** Rejected for the present design because process lifecycle, management projection, provider registration, and native UI are one Desktop capability, while the external executable already has its own fork. A second Gestalt repository would add a protocol and release boundary without an independently evolving consumer.

**Register one DSH provider per account vendor or retain Composite.** Rejected because CLIProxyAPI exposes one inference gateway and one model catalog. Account sources are routing inputs inside the core, not independent adapter authorities in Harness.

**Expose the generic management API to the browser client.** Rejected because it would widen the renderer from a product UI into an administrator for arbitrary core operations and would make management credentials reachable from browser code.

**Statically port the LGPL Go implementation into the MIT fork.** Kept as a higher-cost alternative. It can satisfy the GLM requirement, but the release must carry the applicable combined-work relinking and accompanying-material obligations, and every upstream sync must maintain the mixed-license boundary. Independent implementation from protocol facts is preferred when the complete field report shows that path is practical.

**Synthesize a single quota percentage for every provider.** Rejected because the upstream evidence is heterogeneous. A uniform number would erase missing fields and misrepresent unknown capacity or time windows.

## Consequences

Shipped Desktop Settings renders the built-in account pool rather than an Offer card. The leftover Sub2API installer, sources writer, catalog, sidecar gitlink, and e2e lane are retired. Old `$DSH_HOME/sub2api` user data is neither read nor physically deleted.

A built-in binary increases Desktop Bundle size and makes each supported platform part of the core build matrix. Native runners must establish CGO and dynamic-library closure instead of assuming cross-compilation. Packaging preparation may build and inspect unsigned artifacts, but codesign, notarization, stapler validation, tag creation, release publication, and deployment remain outside this authorization.

Upstream management endpoints and auth-file fields may change faster than the Gestalt UI. The narrow Host gateway limits the affected code, but every fork update still needs protocol and redaction review.

A fork-carried GLM implementation can make upstream synchronization conflict-prone. Independent implementation reduces the mixed-license burden but still requires accurate protocol facts and clean-room discipline; static porting remains available at the cost of the verified LGPL distribution obligations. The verified field and license report fixes that choice without removing GLM from scope.

Provider-specific quota probes may consume upstream requests, trigger rate limits, or expose only approximate data. The fixed Host policies exclude paid inference probes, retain bounded refresh and cache behavior, and prefer an explicit unknown or stale state over aggressive refresh.

The accepted GUI evidence mode is real isolated Electron automation through WDIO, driven only by the designated acceptance owner against the exact reviewed product or prototype revision. This user-authorized mode does not claim that native computer use is permanently unavailable. The evidence records its driver and limits, and GUI screenshots plus the experience route remain required before the UI specification freezes. This walk does not block the non-GUI runtime or provider foundation.
